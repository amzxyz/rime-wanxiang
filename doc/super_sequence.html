    手动排序 (Super Sequence)：调整候选词顺序¶

    super_sequence.lua 用于记录并恢复用户主动调整过的候选位置。它不会改变词频本身，而是在候选输出阶段，根据当前输入编码对应的排序记录重新安排候选顺序。

    当某个候选的位置长期不符合自己的使用习惯时，可以直接在候选菜单中将它前移、后移、置顶，或者取消已有的手动排序。

    当前版本已经改为基于 Rime UserDb 原生记录格式 保存排序状态，并采用稀疏记录方式：只保存真正被用户主动操作过的候选，不再把因其他候选移动而被动让位的普通候选全部写入数据库。

    一、核心快捷键¶

    出现候选菜单后，先选中需要调整的候选，再使用以下快捷键：

    手动排序快捷键

    • Ctrl + p：置顶
      将当前选中的候选移动到第 1 位，并保存这一排序意图。

    • Ctrl + j：向前移动
      将当前选中的候选向前移动 1 个位置。

    • Ctrl + k：向后移动
      将当前选中的候选向后移动 1 个位置。

    • Ctrl + l：重置排序
      取消当前候选已有的手动排序状态，使它重新按照上游候选顺序参与排列。

    例如原始候选为：

    1. 时间
2. 实践
3. 事件
4. 十件

    选中“事件”后按一次 Ctrl + j：

    1. 时间
2. 事件
3. 实践
4. 十件

    再次按 Ctrl + j：

    1. 事件
2. 时间
3. 实践
4. 十件

    如果直接按 Ctrl + p，则会将当前选中的候选直接放到首位。

    二、手动排序不会修改原始词频¶

    Super Sequence 并不是去修改词典频率，也不会把当前候选重新学习成更高词频。

    它的处理方式可以理解为：

    Rime 生成原始候选
        ↓
读取当前编码对应的手动排序记录
        ↓
把已记录的候选放回指定位置
        ↓
其余普通候选按原有顺序填充空位

    因此：

    • 没有手动调整过的候选仍然遵循原有排序逻辑。
    • 用户词频、语法模型、上下文调频仍然可以正常工作。
    • Super Sequence 只对已经明确保存过位置的候选进行额外的位置约束。

    这也是手动排序与普通“调频”的主要区别：

    调频改变候选自身的权重倾向，手动排序保存的是指定输入下的候选位置。

    三、新版采用稀疏记录¶

    旧版本在移动一个候选时，可能会把整段受影响候选的位置一起写入排序数据库。

    例如：

    A
B
C
D
E

    如果把 D 移到第 1 位：

    D
A
B
C
E

    从视觉上看，A / B / C 都向后移动了。

    但新版不会因为这种被动让位，就为 A / B / C 全部创建新的排序记录。

    当前规则是：

    1. 主动操作的候选必须保存。
    2. 从未被主动排序过的普通候选，只在当前候选列表中自然让位，不落库。
    3. 如果另一个候选本来就有手动排序记录，并因为本次操作被挤动，则只更新这个已有记录的最终位置。

    因此数据库中保存的是：

    用户真正表达过的排序意图

    而不是：

    每次移动后整个候选列表的完整快照

    这样可以减少排序数据库中的冗余记录，也能降低多设备同步时不必要的数据变化。

    四、排序记录如何保存？¶

    默认数据库配置为：

    super_sequence:
  db_name: lua/sequence

    当前版本使用 UserDb 的标准记录形式保存每一个手动排序状态。

    逻辑上，一条记录由：

    输入编码 + 候选标识

    唯一确定。

    普通拼音候选可以理解为：

    输入编码 + 候选文字

    例如：

    sj + 时间
sj + 实践

    属于两条不同的排序记录。

    排序状态不再依赖业务时间戳¶

    新版已经取消旧版：

    updated_at
→ 比较最后修改时间
→ 决定哪台设备的数据更新

    这一套由脚本自行维护的时间戳合并逻辑。

    当前排序状态直接编码在 UserDb 标准记录的 c 字段中：

    c = 逻辑版本 + 最终位置状态

    而 UserDb 的：

    t

    交给 librime 自身维护，Super Sequence 不再把它作为业务排序时间戳使用。

    这意味着新版不再需要脚本额外维护“哪个设备最后一次修改发生在几点几分几秒”的时序关系。

    五、Ctrl + l 为什么不是直接删除数据库记录？¶

    从使用效果看：

    Ctrl + l

    就是取消手动排序，让候选重新回到自然排序。

    但数据库层并不是简单地把这条记录物理删除。

    当前版本会写入一个更高逻辑版本的重置墓碑。

    可以理解为：

    旧设备：
这个候选应该固定在第 1 位

新设备：
这个候选已经取消手动排序

    如果“取消排序”只是在本地删除记录，那么旧设备同步过来的历史状态可能再次把它恢复成第 1 位。

    因此新版会保留一条：

    这个排序已经被重置

    的状态记录。

    它的作用是让“取消排序”本身也能够作为一次有效状态参与 UserDb 同步，从而覆盖更早的排序结果。

    重置的是排序效果，不是简单删除一行数据

    Ctrl + l 后，当前候选不再受到这条手动排序记录的约束。

    数据库中保留重置状态，是为了避免多设备同步时旧排序重新出现。

    六、多设备同步：改为使用 UserDb 原生机制¶

    当前版本已经取消旧版自建的排序同步流程。

    旧版曾经需要：

    sequence_device_list.txt
sequence_windows.txt
sequence_mac.txt
sequence_deepin.txt

    并由 Lua 自行：

    导出文本
→ 读取多个设备文件
→ 比较 updated_at 时间戳
→ 合并最新状态
→ 再写回本地数据库

    这一套现在已经不再作为 Super Sequence 的日常运行机制。

    新版直接把排序信息保存成稳定的 UserDb 记录，使其能够跟随 Rime 原有的用户数据同步流程处理。

    因此新用户不需要再：

    • 为 Super Sequence 单独创建 sequence_device_list.txt
    • 手工维护 sequence_windows.txt、sequence_mac.txt 等设备文件
    • 为排序脚本单独建立“主设备”
    • 依赖 Lua 自己比较 updated_at
    • 把合并后的文本再次注入 sequence.userdb

    当前同步思路¶

    可以简化为：

    本机手动排序
      ↓
写入 UserDb
      ↓
按照正常 Rime 用户数据同步流程同步
      ↓
其他设备获得对应排序状态

    其中：

    • 正常排序状态带有自己的逻辑版本。
    • 再次调整会递增该候选自己的逻辑版本。
    • Ctrl + l 会写入更高版本的重置墓碑。
    • 业务层不再依赖设备本地时间来判断新旧。

    这也是新版取消旧时序合并逻辑后的主要变化。

    七、自定义按键与数据库¶

    当前 Super Sequence 对外主要提供以下配置：

    super_sequence:
  db_name: "lua/sequence"
  up: "Control+j"
  down: "Control+k"
  reset: "Control+l"
  pin: "Control+p"

    如果需要修改，可以在 wanxiang.custom.yaml 中 Patch：

    patch:
  "super_sequence/db_name": "lua/sequence"
  "super_sequence/up": "Control+j"
  "super_sequence/down": "Control+k"
  "super_sequence/reset": "Control+l"
  "super_sequence/pin": "Control+p"

    各参数含义：

    参数 作用 默认值
    db_name 排序 UserDb 数据库名称 lua/sequence
    up 当前候选向前移动一位 Control+j
    down 当前候选向后移动一位 Control+k
    reset 取消当前候选手动排序 Control+l
    pin 当前候选置顶 Control+p

    当前没有需要用户配置的：

    同步设备清单
排序时间戳
导出间隔
自动合并周期
sequence_设备名.txt

    这些都属于旧版同步实现，不应再写入当前配置教程。

    Super Sequence 只记录明确的排序意图：普通候选按文字记位置，动态候选按格式序号记位置，其余候选继续保持原有排序逻辑。
